# PostgreSQL Database Schema for 10xCards

This document outlines the comprehensive database schema for the 10xCards application, designed for PostgreSQL and managed via Supabase.

## 1. Tables

### 1.1. `public.flashcards`

The central table for storing all flashcard data, including content and spaced repetition metadata based on the SM-2 algorithm.

| Column          | Data Type     | Constraints & Defaults                                                     | Description                                                                                                             |
| --------------- | ------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `id`            | `uuid`        | `PRIMARY KEY`, `DEFAULT uuid_generate_v4()`                                | Unique identifier for the flashcard.                                                                                    |
| `user_id`       | `uuid`        | `NOT NULL`, `REFERENCES auth.users(id) ON DELETE CASCADE`                  | Foreign key linking to the user who owns the flashcard.                                                                 |
| `front`         | `text`        | `NOT NULL`, `CHECK (char_length(front) > 0 AND char_length(front) <= 200)` | The front side (question) of the flashcard. Max 200 characters.                                                         |
| `back`          | `text`        | `NOT NULL`, `CHECK (char_length(back) > 0 AND char_length(back) <= 400)`   | The back side (answer) of the flashcard. Max 400 characters.                                                            |
| `created_by_ai` | `boolean`     | `NOT NULL`, `DEFAULT false`                                                | Flag indicating if the flashcard was generated by AI.                                                                   |
| `generation_id` | `uuid`        | `NULLABLE`, `REFERENCES public.generations(id) ON DELETE SET NULL`         | Optional foreign key linking to the generation event that created this flashcard. NULL for manually created flashcards. |
| `repetition`    | `integer`     | `NOT NULL`, `DEFAULT 0`                                                    | The number of times the card has been successfully recalled in a row.                                                   |
| `interval`      | `integer`     | `NOT NULL`, `DEFAULT 0`                                                    | The number of days to wait before the next review.                                                                      |
| `efactor`       | `numeric`     | `NOT NULL`, `DEFAULT 2.5`                                                  | The easiness factor, used by the SM-2 algorithm to determine the next interval.                                         |
| `due_date`      | `timestamptz` | `NOT NULL`, `DEFAULT now()`                                                | The date when the flashcard is scheduled for the next review.                                                           |
| `created_at`    | `timestamptz` | `NOT NULL`, `DEFAULT now()`                                                | Timestamp of when the flashcard was created.                                                                            |
| `updated_at`    | `timestamptz` | `NOT NULL`, `DEFAULT now()`                                                | Timestamp of the last update, automatically managed by a trigger.                                                       |

### 1.2. `public.generations`

Immutable table for tracking AI flashcard generation events. Each record represents a single AI generation session.

| Column                       | Data Type       | Constraints & Defaults                                                                       | Description                                                                                                     |
| ---------------------------- | --------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `id`                         | `uuid`          | `PRIMARY KEY`, `DEFAULT uuid_generate_v4()`                                                  | Unique identifier for the generation event.                                                                     |
| `user_id`                    | `uuid`          | `NOT NULL`, `REFERENCES auth.users(id) ON DELETE CASCADE`                                    | Foreign key linking to the user who initiated the generation.                                                   |
| `source_text`                | `text`          | `NOT NULL`, `CHECK (char_length(source_text) >= 1000 AND char_length(source_text) <= 10000)` | The source text provided by the user for AI generation. Min 1000, max 10000 characters as per PRD requirements. |
| `context`                    | `text`          | `NULLABLE`                                                                                   | Optional context/topic provided by the user to improve AI generation quality.                                   |
| `ai_model`                   | `text`          | `NOT NULL`                                                                                   | Identifier of the AI model used for generation (e.g., "gpt-4", "claude-3").                                     |
| `generation_time_ms`         | `integer`       | `NOT NULL`, `CHECK (generation_time_ms >= 0)`                                                | Time taken to generate flashcards in milliseconds.                                                              |
| `flashcards_generated_count` | `integer`       | `NOT NULL`, `CHECK (flashcards_generated_count >= 0)`                                        | Number of flashcards successfully generated in this event.                                                      |
| `cost`                       | `numeric(10,6)` | `NOT NULL`, `DEFAULT 0`, `CHECK (cost >= 0)`                                                 | Cost of the API call in USD. Stored with 6 decimal precision for accurate tracking.                             |
| `created_at`                 | `timestamptz`   | `NOT NULL`, `DEFAULT now()`                                                                  | Timestamp of when the generation event was completed.                                                           |

**Note**: This table is immutable by design - no `updated_at` column. Records are created only after successful generation.

## 2. Relationships

### 2.1. User Relationships

- **`auth.users` to `public.flashcards`**: One-to-many relationship.
  - **Cardinality**: One user can own many flashcards.
  - **Implementation**: Foreign key `user_id` in `flashcards` references `auth.users(id)`.
  - **Referential Integrity**: `ON DELETE CASCADE` - when a user is deleted, all their flashcards are automatically removed.

- **`auth.users` to `public.generations`**: One-to-many relationship.
  - **Cardinality**: One user can initiate many generation events.
  - **Implementation**: Foreign key `user_id` in `generations` references `auth.users(id)`.
  - **Referential Integrity**: `ON DELETE CASCADE` - when a user is deleted, all their generation records are automatically removed.

### 2.2. Generation-Flashcard Relationship

- **`public.generations` to `public.flashcards`**: One-to-many relationship.
  - **Cardinality**: One generation event can create many flashcards.
  - **Implementation**: Optional foreign key `generation_id` in `flashcards` references `generations(id)`.
  - **Referential Integrity**: `ON DELETE SET NULL` - when a generation record is deleted, associated flashcards remain but their `generation_id` is set to NULL.
  - **Business Logic**: `generation_id` is NULL for manually created flashcards and populated for AI-generated flashcards.

## 3. Indexes

Optimized indexes for common query patterns:

### 3.1. Flashcards Table Indexes

- **`flashcards_user_due_date_idx`**
  - **Type**: B-tree (composite)
  - **Columns**: `(user_id, due_date)`
  - **Purpose**: Optimizes learning session queries fetching flashcards due for review.
  - **Query Pattern**: `WHERE user_id = '...' AND due_date <= now()`

- **`flashcards_generation_id_idx`**
  - **Type**: B-tree
  - **Columns**: `(generation_id)`
  - **Purpose**: Optimizes queries fetching all flashcards from a specific generation event.
  - **Query Pattern**: `WHERE generation_id = '...'`
  - **Note**: Supports NULL values for manually created flashcards.

### 3.2. Generations Table Indexes

- **`generations_user_id_idx`**
  - **Type**: B-tree
  - **Columns**: `(user_id)`
  - **Purpose**: Optimizes queries fetching generation history for a specific user.
  - **Query Pattern**: `WHERE user_id = '...'`
  - **Use Case**: Analytics, user generation history, cost tracking.

- **`generations_created_at_idx`**
  - **Type**: B-tree
  - **Columns**: `(created_at DESC)`
  - **Purpose**: Optimizes queries fetching recent generations in chronological order.
  - **Query Pattern**: `ORDER BY created_at DESC`
  - **Use Case**: Admin dashboards, recent activity feeds.

## 4. PostgreSQL Policies (Row-Level Security)

### 4.1. Flashcards Table RLS

RLS is enabled to ensure users can only access their own flashcards.

```sql
ALTER TABLE public.flashcards ENABLE ROW LEVEL SECURITY;
```

#### Policies for `anon` role (unauthenticated users):

- **SELECT Policy**: `anon_users_cannot_view_flashcards`
  - Denies all SELECT operations
  - Condition: `false`

- **INSERT Policy**: `anon_users_cannot_create_flashcards`
  - Denies all INSERT operations
  - Condition: `false`

- **UPDATE Policy**: `anon_users_cannot_update_flashcards`
  - Denies all UPDATE operations
  - Condition: `false`

- **DELETE Policy**: `anon_users_cannot_delete_flashcards`
  - Denies all DELETE operations
  - Condition: `false`

#### Policies for `authenticated` role (logged-in users):

- **SELECT Policy**: `authenticated_users_can_view_own_flashcards`
  - Allows users to view only their own flashcards
  - Condition: `(select auth.uid()) = user_id`

- **INSERT Policy**: `authenticated_users_can_create_own_flashcards`
  - Allows users to create flashcards only for themselves
  - Condition: `(select auth.uid()) = user_id`

- **UPDATE Policy**: `authenticated_users_can_update_own_flashcards`
  - Allows users to update only their own flashcards
  - Condition: `(select auth.uid()) = user_id` (both USING and WITH CHECK)

- **DELETE Policy**: `authenticated_users_can_delete_own_flashcards`
  - Allows users to delete only their own flashcards
  - Condition: `(select auth.uid()) = user_id`

### 4.2. Generations Table RLS

RLS is enabled to ensure users can only access their own generation records.

```sql
ALTER TABLE public.generations ENABLE ROW LEVEL SECURITY;
```

#### Policies for `anon` role (unauthenticated users):

- **DELETE Policy**: `anon_users_cannot_delete_generations`
  - Denies all DELETE operations
  - Condition: `false`

#### Policies for `authenticated` role (logged-in users):

- **SELECT Policy**: `authenticated_users_can_view_own_generations`
  - Allows users to view only their own generation records
  - Condition: `(select auth.uid()) = user_id`

- **INSERT Policy**: `authenticated_users_can_create_own_generations`
  - Allows users to create generation records only for themselves
  - Condition: `(select auth.uid()) = user_id`

- **UPDATE Policy**: `authenticated_users_can_update_own_generations`
  - Allows users to update only their own generation records
  - Condition: `(select auth.uid()) = user_id` (both USING and WITH CHECK)
  - **Note**: While the table is designed to be immutable, this policy allows for edge cases.

- **DELETE Policy**: `authenticated_users_can_delete_own_generations`
  - Allows users to delete only their own generation records
  - Condition: `(select auth.uid()) = user_id`

## 5. Triggers and Functions

### 5.1. Updated Timestamp Automation for Flashcards

Automatically updates the `updated_at` column whenever a flashcard is modified.

```sql
CREATE OR REPLACE FUNCTION public.handle_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER on_flashcards_update
  BEFORE UPDATE ON public.flashcards
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_updated_at();
```

## 6. Design Decisions and Rationale

### 6.1. Normalization Level

The schema follows **Third Normal Form (3NF)** principles:

- All tables have atomic columns
- No partial dependencies on composite keys
- No transitive dependencies
- Minimal data redundancy

### 6.2. Generations Table Design

**Why immutable?**

- Generation events are historical records that should not be modified
- Simplifies auditing and analytics
- Eliminates the need for `updated_at` tracking
- Records are created only after successful generation completion

**Why store `flashcards_generated_count`?**

- Enables quick analytics without joining to flashcards table
- Supports metrics tracking (PRD requirement: 75% acceptance rate)
- Denormalization justified by performance benefits for read-heavy analytics

**Why store `cost`?**

- Strategic requirement for future cost optimization
- Enables per-user, per-model cost analysis
- Supports billing and usage monitoring
- High precision (6 decimals) for accurate API cost tracking

### 6.3. Optional `generation_id` in Flashcards

**Why nullable?**

- Supports both AI-generated and manually created flashcards
- Maintains data integrity: flashcards can exist independently
- `ON DELETE SET NULL` preserves flashcards even if generation record is removed

**Relationship with `created_by_ai`:**

- `created_by_ai = true` → flashcard was AI-generated (may or may not have `generation_id`)
- `generation_id NOT NULL` → flashcard is linked to a specific generation event
- Both flags work together for comprehensive tracking

### 6.4. Character Length Constraints

All constraints align with PRD requirements:

- Source text: 1000-10000 characters (PRD requirement)
- Flashcard front: max 200 characters (PRD requirement)
- Flashcard back: max 400 characters (PRD requirement)
- Enforced at database level for data integrity

### 6.5. Security Architecture

**Multi-layered approach:**

1. **Row-Level Security (RLS)**: Data isolation at database level
2. **Role-based policies**: Separate policies for `anon` and `authenticated` roles
3. **Cascade deletion**: Automatic cleanup when users are removed
4. **Foreign key constraints**: Referential integrity enforcement

**Performance consideration:**

- RLS policies use optimized equality checks (`(select auth.uid()) = user_id`)
- The subquery wrapper ensures `auth.uid()` is evaluated once per query, not per row
- Indexed foreign keys prevent performance degradation
- Policies are evaluated efficiently by PostgreSQL

### 6.6. Scalability Considerations

**Indexes strategy:**

- Composite indexes for multi-column queries (user_id + due_date)
- Single-column indexes for foreign keys and frequent filters
- Descending index on `created_at` for recent-first queries

**Growth projections:**

- Flashcards: High write/read ratio, frequent updates
- Generations: Write-once, read-occasionally, archive-friendly
- Indexes support expected query patterns at scale

**Future optimization opportunities:**

- Partition `flashcards` by user_id if user base grows significantly
- Archive old `generations` records (>1 year) to cold storage
- Add materialized views for complex analytics queries

## 7. Success Metrics Support

The schema directly supports PRD-defined success metrics:

### 7.1. AI Acceptance Rate Tracking

**Metric**: 75% of AI-generated flashcards are accepted without modification

**Schema support:**

- `generations.flashcards_generated_count`: Total flashcards generated
- `flashcards.generation_id`: Links flashcards to generation event
- `flashcards.created_by_ai`: Identifies AI-generated flashcards
- `flashcards.updated_at` vs `flashcards.created_at`: Detects post-generation edits

**Query pattern:**

```sql
SELECT
  g.id,
  g.flashcards_generated_count as total_generated,
  COUNT(f.id) as accepted_count,
  COUNT(CASE WHEN f.updated_at > f.created_at + INTERVAL '5 minutes' THEN 1 END) as edited_count
FROM generations g
LEFT JOIN flashcards f ON f.generation_id = g.id
GROUP BY g.id;
```

### 7.2. AI Utilization Rate

**Metric**: 75% of all flashcards are created using AI

**Schema support:**

- `flashcards.created_by_ai`: Boolean flag for AI-generated flashcards

**Query pattern:**

```sql
SELECT
  COUNT(*) FILTER (WHERE created_by_ai = true)::float / COUNT(*) as ai_utilization_rate
FROM flashcards;
```

## 8. Migration Strategy

For production deployment:

1. **Create generations table first** (no dependencies)
2. **Add generation_id column to flashcards** (with foreign key)
3. **Create all indexes** (after data is loaded if migrating)
4. **Enable RLS and create policies** (last step to avoid permission issues)
5. **Verify policies with test queries** (ensure security is working)

## 9. Backup and Maintenance

**Recommended practices:**

- Daily automated backups via Supabase
- Weekly manual backup verification
- Monitor index usage and rebuild if fragmented
- Archive generations older than 1 year (optional)
- Regular `VACUUM ANALYZE` for query performance
