# PostgreSQL Database Schema for 10xCards

This document outlines the database schema for the 10xCards application, designed for PostgreSQL and managed via Supabase.

## 1. Tables

### `public.flashcards`

This is the central table for storing all flashcard data, including content and spaced repetition metadata.

| Column          | Data Type     | Constraints & Defaults                                                                                               | Description                                                                 |
|-----------------|---------------|----------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------|
| `id`              | `uuid`        | `PRIMARY KEY`, `DEFAULT uuid_generate_v4()`                                                                          | Unique identifier for the flashcard.                                        |
| `user_id`         | `uuid`        | `NOT NULL`, `REFERENCES auth.users(id) ON DELETE CASCADE`                                                            | Foreign key linking to the user who owns the flashcard.                     |
| `front`           | `text`        | `NOT NULL`, `CHECK (char_length(front) > 0 AND char_length(front) <= 500)`                                            | The front side (question) of the flashcard.                                 |
| `back`            | `text`        | `NOT NULL`, `CHECK (char_length(back) > 0 AND char_length(back) <= 1000)`                                           | The back side (answer) of the flashcard.                                    |
| `created_by_ai`   | `boolean`     | `NOT NULL`, `DEFAULT false`                                                                                          | Flag indicating if the flashcard was generated by AI.                       |
| `repetition`      | `integer`     | `NOT NULL`, `DEFAULT 0`                                                                                              | The number of times the card has been successfully recalled in a row.       |
| `interval`        | `integer`     | `NOT NULL`, `DEFAULT 0`                                                                                              | The number of days to wait before the next review.                          |
| `efactor`         | `numeric`     | `NOT NULL`, `DEFAULT 2.5`                                                                                            | The easiness factor, used by the SM-2 algorithm to determine the next interval. |
| `due_date`        | `timestamptz` | `NOT NULL`, `DEFAULT now()`                                                                                          | The date when the flashcard is scheduled for the next review.               |
| `created_at`      | `timestamptz` | `NOT NULL`, `DEFAULT now()`                                                                                          | Timestamp of when the flashcard was created.                                |
| `updated_at`      | `timestamptz` | `NOT NULL`, `DEFAULT now()`                                                                                          | Timestamp of the last update, automatically managed by a trigger.           |

## 2. Relationships

- **`auth.users` to `public.flashcards`**: A one-to-many relationship.
  - **Cardinality**: One user can have many flashcards.
  - **Implementation**: A foreign key `user_id` in the `flashcards` table references the `id` in Supabase's `auth.users` table.
  - **Referential Integrity**: `ON DELETE CASCADE` is enabled. When a user is deleted from `auth.users`, all their associated flashcards in `public.flashcards` are automatically deleted.

## 3. Indexes

To optimize the primary query for fetching flashcards due for review, a composite index is created.

- **`flashcards_user_due_date_idx`**
  - **Type**: B-tree
  - **Columns**: `(user_id, due_date)`
  - **Purpose**: Speeds up queries that filter flashcards for a specific user that are due on or before the current date (e.g., `WHERE user_id = '...' AND due_date <= now()`).

## 4. PostgreSQL Policies (Row-Level Security)

RLS is enabled on the `flashcards` table to ensure users can only access their own data.

- **Enable RLS**
  ```sql
  ALTER TABLE public.flashcards ENABLE ROW LEVEL SECURITY;
  ```

- **SELECT Policy**
  ```sql
  CREATE POLICY "Users can view their own flashcards" 
  ON public.flashcards FOR SELECT
  USING (auth.uid() = user_id);
  ```

- **INSERT Policy**
  ```sql
  CREATE POLICY "Users can create their own flashcards" 
  ON public.flashcards FOR INSERT
  WITH CHECK (auth.uid() = user_id);
  ```

- **UPDATE Policy**
  ```sql
  CREATE POLICY "Users can update their own flashcards" 
  ON public.flashcards FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);
  ```

- **DELETE Policy**
  ```sql
  CREATE POLICY "Users can delete their own flashcards" 
  ON public.flashcards FOR DELETE
  USING (auth.uid() = user_id);
  ```

## 5. Additional Considerations

- **`updated_at` Automation**: A trigger function should be implemented to automatically update the `updated_at` column whenever a row in the `flashcards` table is modified. This is a standard practice for tracking record changes.
  ```sql
  -- Function to update the timestamp
  CREATE OR REPLACE FUNCTION handle_updated_at() 
  RETURNS TRIGGER AS $$
  BEGIN
    NEW.updated_at = now();
    RETURN NEW; 
  END;
  $$ LANGUAGE plpgsql;

  -- Trigger to call the function before any update
  CREATE TRIGGER on_flashcards_update
    BEFORE UPDATE ON public.flashcards
    FOR EACH ROW
    EXECUTE PROCEDURE handle_updated_at();
  ```

- **Role Permissions**: The `anon` role should have no permissions on the `flashcards` table, while the `authenticated` role will be granted `SELECT`, `INSERT`, `UPDATE`, and `DELETE` permissions, which are then restricted by the RLS policies.
